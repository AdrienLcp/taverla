# Stage 07 — A French UI

**Goal.** Decide whether this game speaks French, and if so, build the layer
that lets it.

**Depends on** nothing. Cheapest before stage 05 hard-codes strings into a
design, and much more expensive after.

## The decision, stated plainly

The UI is currently **English**, because the repository rule is that everything
committed is written in English unless the UI is explicitly internationalised.
That rule is doing its job here — it stopped French strings being scattered
through components with no layer to hold them.

But the actual product is a party game played in France with French friends, and
"Waiting for the host" is worse than "En attente de l'hôte" for every person who
will ever use it. So the honest position is: the current state is *compliant*,
not *right*, and this stage is where that gets fixed properly.

Three options:

| | Cost | Result |
|---|---|---|
| Keep English | none | Compliant, mildly wrong for the audience |
| Full i18n layer, French default | ~half a session | Compliant *and* right; strings live in one file |
| Swap the literals to French | ~an hour | Right, and breaks the rule with no layer to justify it |

**Recommended: the middle one.** It is the only option that satisfies both the
rule and the players, and at this size the layer is genuinely small.

## Work, if the layer is built

**`apps/game/src/presentation/i18n/`** — a dictionary per locale, a `useTranslate`
hook, `fr-FR` as the default. No library: this is a few dozen strings with no
plural rules worth pulling a dependency for. Add one when a real need appears
(dates, plurals, gendered agreement), not before.

`@react-aria/optimize-locales-plugin` is already configured for `en-US` and
`fr-FR` in `vite.config.ts`, so react-aria's own strings — the ones inside
`FieldError`, press announcements, `role="status"` regions — are covered.

**Strings the server owns.** Every `protocolErrorMessageSchema` message is
written server-side, in English, and shown to the user. Either the client maps
`code` → translated string and ignores `message` (cleaner — the code is already
a closed enum), or the server learns a locale. **Prefer the first**; the codes
exist for exactly this.

That is worth doing even if the UI stays English: a user-facing string arriving
from a server is a design smell, and `message` becomes what it should have been
all along — a developer-facing detail.

## Careful with

- **Room codes are not translatable**, and the alphabet excludes accented
  characters by construction. Do not let a normaliser start folding `É` to `E`.
- **A locale switch must not remount the socket.** It is not in the hook's
  dependencies today; keep it that way.
- **French is longer than English** — typically 15–20%. The host's room code is
  fine, but button labels and the buzzer's blocker line will grow. Check the
  414 px layout after translating, not before.

## Done when

- Every user-visible string comes from the dictionary
- Server error codes are translated client-side; `message` is no longer rendered
- The 414 px and 1920 px layouts survive the longer strings
- The rule in `.claude/CLAUDE.md` is updated to record that the UI is now
  explicitly internationalised

## Out of scope

A locale picker, right-to-left, translated track metadata (Deezer's is whatever
the label filed).
